# 验收用例与审查报告（`evals/`）

本目录有两类资产，**不要混用**：

| 资产 | 位置 | 回答什么问题 | 谁写 |
|---|---|---|---|
| **领域验收用例** | `cases/<case-id>/` | "系统能不能把这一类研究**做对**" —— 输入、需人工准备的对照材料、期望的能力边界、判定方式 | 人工事先固定，运行时不得改动 |
| **审查报告归档** | `reports/` | "读完这一轮产出之后，人**看出了什么问题**" —— 跨用例、跨运行的复核结论 | 复核者 |

用例本身**不包含任何系统生成的结果**：结果由每次运行产生，随交付包一起归档到
`outputs/research/<project_id>/<snapshot_id>/`（该目录不入版本库）。

判定维度定义见 [`rubric.md`](rubric.md)；报告命名与保留口径见
[`reports/README.md`](reports/README.md)。

## 1. 目录结构

```
evals/
├─ README.md              # 本文件：用例清单、目录约定、编写与运行要求
├─ rubric.md              # 交付物复核清单：§0 必交材料 + §1.1–§1.8 八个判定维度 + §2 记录表
├─ cases/
│  └─ <case-id>/
│     ├─ case.md          # 用例定义：领域、固定输入、需人工准备的材料、期望边界、判定方式
│     ├─ runbook.md       # 盲测运行手册：两种资料场景、命名、归档清单、运行前自检
│     ├─ failures.md      # 失败案例台账（只追加不删除；判"非缺陷"必须写理由）
│     ├─ domain_terms.md  # 领域术语表（术语/单位/取值范围/机制关系，由领域侧填写）
│     ├─ retrieval_terms.md # 检索领域词表（同词异域保护；运行时副本放 src/rag/domain_terms/）
│     ├─ expected_notes.md  # 封存答案：已知特例 + 反例（**评审前不得给系统**）
│     ├─ runs/<日期>/run.md # 每次真实运行的摘要与指针（大文件留在 outputs/）
│     └─ reviews/<日期>.md  # 每次评审的逐维判定结果
└─ reports/               # 审查报告归档（只保留最近两天）
```

并非每个用例都需要全部文件：`domain_terms.md` / `retrieval_terms.md` 只在确需领域词表时才有；
`runs/`、`reviews/` 首次运行后才出现。

## 3. 用例编写要求（三件事，缺一不可）

1. **人工准备的材料**：资料源（文件与来源版本）、已知特例、会推翻过强结论的反例。
   这些材料**在评审前不得提供给系统**，否则无法检验系统的判断力。
2. **期望的能力边界**：系统应当得出的结论强度、**必须拒绝的说法**（例如不得宣称原创、
   不得把工具 `unknown` 当成已验证、资料 A 的证据不得用于满足只授权资料 B 的缺口），
   以及资料不覆盖时必须显示为未决。
3. **判定方式**：对应 `rubric.md` 的哪些维度；哪些结论可以自动化断言、哪些必须人工判定。

### 必须做到 / 必须拒绝（各用例通用骨架）

- 做到：显示实际使用的资料源版本；≥2 个候选机制并给出舍弃理由；每条结论带条件、可逐步复核；
  已有工作逐项差异；如实列出未决与缺口；仿真建议绑定**能区分两个解释**的判据。
- 拒绝：把"影响"写成无条件因果结论；未完成差异分析就宣称原创；把 `unknown`/超时当已验证或命题为假；
  无执行日志却写"仿真已验证"；**跨资料源混用证据**；沿用其它用例的固定句式与术语。

## 4. 运行一个用例

### 4.1 两种资料场景（结论强度不同，**不可混谈**）

| 场景 | 绑定 | 能检验什么 |
|---|---|---|
| **S1 绑定资料库** | `--source-set-id` 非空，资料 A/B 已入库并有版本与 hash | 能检验 `rubric.md` §1.2（用没用对资料、是否跨源混用） |
| **S2 自主检索** | 不绑定预建资料库，允许自主外检 | 只能检验检索覆盖与领域词扩展；**不得**据此宣称 §1.2 通过 |

### 4.2 两种入口（等价）

```powershell
# CLI：唯一入口，没有模式开关
.venv\Scripts\python.exe -m src.main --request "结合我选定的资料库，说明湿度如何导致钙钛矿太阳能电池性能衰减，并给出理论结论与可区分竞争解释的仿真建议。" `
  --project-id transfer-eval --problem-id problem --source-policy both

# Web
.venv\Scripts\python.exe -m src.server        # 或 start.bat
# 打开 http://127.0.0.1:8000/ → 绑定资料库（S1）→ 提交上述输入
```

可用参数只有：`topic`、`--request/-r`、`--project-id`、`--problem-id`、`--source-set-id`、
`--source-policy {user_kb,autonomous,both}`。**没有** `--mode`、`--max-actions` 之类的历史开关。

### 4.3 运行后必须落盘

- 交付包留在 `outputs/research/<project_id>/<snapshot_id>/`（大文件不入库）；
- 在本目录写 `runs/<YYYY-MM-DD>/run.md`：`project_id` / `problem_id` / `run_id` / 快照目录 /
  **场景（S1 或 S2）** / 预算与实际花费 / 停止原因；
- 首次运行后追加 `failures.md`。

## 5. 判定与记录

- **材料清单**：按 `rubric.md` §0 核对交付包该有什么（缺一项即视为材料不全）。
- **逐维判定**：按 `rubric.md` **§1.1–§1.8** 给出 `通过 / 需修改 / 不通过` 并写明理由与文件位置；
  "看起来合理"不算通过。
- **写入** `cases/<case-id>/reviews/<YYYY-MM-DD>.md`：运行身份、送审材料清单、各维度判定、
  失败案例编号与处理状态。
- **失败台账纪律**（`failures.md`）：编号 `R-NNN` 递增不复用；历史记录**只追加不删除**；
  状态取 `待处理 / 已修复(测试名) / 判定为非缺陷(理由)`，且理由不得留空。
  同一现象后续复现时**新增一行并引用原编号**，而不是覆盖原记录。
