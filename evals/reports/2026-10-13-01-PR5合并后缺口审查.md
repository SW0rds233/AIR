## 2. 缺口一：master 上一条测试**必然**失败

### 2.1 断言与源码相互矛盾

`tests/test_library_folder_binding.py:143-147`（当前 master）：

```python
denied = client.post("/api/library/scan", json={
    "paths": [str(external)], "allow_roots": [str(external)],
}).json()
assert denied["counts"]["ok"] == 0        # ← "静默忽略"时代的响应形状
```

`src/team_api.py::_scan_request`（当前 master）**明确拒绝**：

```python
if req.allow_roots:
    raise HTTPException(400, "allow_roots 已废弃：网页请求不能自行扩展授权根。"
                             "请在页面用「从文件管理器选取文件夹」授权目标目录，"
                             "或在服务端配置 DATA_READ_ROOTS（分号分隔的绝对路径）。")
```

### 2.2 实测（隔离的临时数据目录，未触碰真实数据）

```
POST /api/library/scan  {"paths":[<外部目录>], "allow_roots":[<同一目录>]}
→ HTTP 400
→ 响应体 {'detail': 'allow_roots 已废弃：网页请求不能自行扩展授权根。…'}
→ 没有 counts 字段  ⇒  denied['counts'] 必然 KeyError
```

全量：**`1 failed, 217 passed`**，失败点 `tests/test_library_folder_binding.py:147`，异常 `KeyError: 'counts'`。

### 2.3 成因

该测试文件在协作者的工作树里是**旧版本**（`allow_roots` 400 改造之前的断言），随合并进入主干；而源码保留 400。二者不同步 → 测试必红。**与运行环境无关**：本机 Python 3.14.4、依赖齐备，其它 217 项全通过。

### 2.4 为什么之前没人处理

协作者 PR #3 的报告里**已经点出这一条**（原话）：

> 「…另 3 项失败：2 项因本机 Python 3.12 与原虚拟环境 Python 3.14 的 Matplotlib 原生模块不兼容；**1 项是既有资料库测试仍期望已废弃的非空 `allow_roots` 返回扫描计数，现有 API 明确返回 HTTP 400**。它们与 writer 改动无关。」

即：**记录为"与本次改动无关的既有失败"，但未修**。于是它在这次合并里正式进入 master。

### 2.5 影响

1. **主干变红**：任何以"全量绿"为前提的自检或未来的 CI 都失效；
2. **掩盖真实回归**：红测试一旦被当成"已知失败"，日后再出问题也容易被同样略过；
3. **语义反了**：这条用例本意是验证"HTTP 请求不能自行扩展授权根"这一**安全行为**，现在它反过来在否定正确行为。

### 2.6 修法

| 方案 | 改动 | 评价 |
|---|---|---|
| **(i) 让测试与新行为一致（推荐）** | `assert denied.status_code == 400`；`assert "allow_roots" in denied.json()["detail"]`；可补 import 接口同样 400 的断言 | 与源码、与安全设计一致 |
| (ii) 让 `allow_roots` 重新生效 | 改 `src/team_api.py` 删掉 400 分支 | **不建议**：等于允许网页请求自行扩展授权根，是安全回退 |

## 3. 缺口二：库名规范化后的选中链路被回退

### 3.1 机制（这条机制本身没有变）

库的**规范 id 就是磁盘目录名**：`sanitize_filename("星网 星链")` = `星网_星链`；`GET /api/sources` 列出的正是目录名。用户输入的库名（可含空格）只用于显示。

### 3.2 实测（隔离环境）

```
用户输入的库名 (topic)       : '探针 库名'
响应里的 source_set_id       : None            ← 该字段已不存在
/api/sources 的 id 集合      : ['探针_库名']
topic 是否等于列表里的某个 id : False
规范化后的目录名             : '探针_库名'
前端将调用 selectSourceSet('探针 库名') → 能否选中: False
```

### 3.3 后果链（三步，逐步升级）

**第 1 步 · UI 自相矛盾。**
`src/web/src/library-controller.ts:263` 现在是 `await deps.selectSourceSet(result.topic);` —— 拿**用户输入的原文**去 `<select>` 里做**逐字比较**。赋一个不存在的值时浏览器把 `value` 置空，于是 `app.ts` 报：

> 资料库已导入，但未能在选择列表中找到该库，请刷新资料库。

而控制器此前已经打印过「**已为下一次研究选中该库**」—— 两条消息互相打脸。

**第 2 步 · 下一次运行实际没有绑定资料库（要害）。**
`src/web/src/features/intake/controller.ts:316`：

```ts
source_set_id: (byId<HTMLSelectElement>('sourceset') && val('sourceset')) || '',
```

启动研究取的**就是那个下拉框的值**。自动选中失败 = `source_set_id` 为空 = **下一次运行没有任何绑定库** → 证据角色检索默认库 → 报「**资料库不可用或为空: 没有可检索的已登记资料**」。这正是 `proj-mv3omgh65ukz` 那次（`source_set_id=""`、102 分钟、8 条义务 7 条 blocked、零结论、无导出）的 P-1 触发条件。而 PR #3 已删除那条"改为 autonomous"的误导性建议，因此现在只剩"空库"一句，用户更难判断问题所在。

**第 3 步 · 缺陷被写入会话记录，续跑复发。**
`src/team_api.py:217` 现在是 `bind_conversation_library(session_id, topic)` —— **存原文**。而 `src/web/src/session-controller.ts:141`：

```ts
const library = String(rec.bound_source_set_id || req.source_set_id || '');
```

恢复历史对话时又用这个原文去选中 → 同样选不中 → **每次续跑都无绑定**。
