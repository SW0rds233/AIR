## 2. 仍然存在的问题

### 【严重】R-1 测试依赖未入库的领域词表 → 干净克隆必挂一条测试

**现象**（干净克隆模拟：把两个未跟踪词表移走后跑全量测试）：

```
FAILED tests/test_shared_research_quality.py::test_perovskite_request_gets_mechanism_contract_and_shared_field
1 failed, 138 passed in 3.34s
```

**依赖点**（`tests/test_shared_research_quality.py`）：

| 行 | 断言 | 依赖 |
|---|---|---|
| 51 | `assert "perovskite solar cell" in terms` | `domain_terms/perovskite-stability.md` 的 `translation:` 行 |
| 54 | `assert build_spec_from_input(...).domain == "perovskite-stability"` | 同文件的 `domain:`/`aliases:` |
| 58 | `assert _topic_of(...) == "shared-perovskite-stability"` | 同上（领域→共享库命名） |

**未跟踪状态**（`git status`）：`tests/test_shared_research_quality.py`、`tests/test_current_run_integrity.py`、
`src/rag/domain_terms/perovskite-stability.md`、`src/rag/domain_terms/combinatorial-design.md` 四个文件均未跟踪。

**风险**：若提交 `tests/` 而漏掉 `src/rag/domain_terms/perovskite-stability.md`，干净克隆上会挂一条测试；
且该词表被 `.gitignore` 之外无任何保护（`data/`、`outputs/` 有忽略规则，`src/rag/domain_terms/` 没有）。

**更根本的一层**：该测试的夹具是**为评测用例撰写的生产数据文件**，其别名文案直接决定断言内容。
生产数据与测试夹具耦合，后续任何人调整领域词表（合法的运维动作）都可能弄挂测试。

**建议**：①词表与测试**成对提交**；②把测试夹具独立出来（`tests/fixtures/domain_terms/` 或注入式词表路径），
让生产词表的变更不再牵动测试；③对 `src/rag/domain_terms/*.md` 增加一条"存在性 + 可解析"的测试。

### 【未修】R-4 义务模板仍按社会科学/统计默认项生成

`research/problem_formulator._applied_obligations()` 对**所有非定义型命题**无条件附加：

```python
statement=f"在声明范围 (人群/地区/时期) 内限定结论: {claim.statement}", kind="scope_check"
```

并对类型追加：

```python
if claim.claim_type == ClaimType.predictive:
    ... "给出样本外评估方案与基线比较", kind="design_feasibility"
```

**后果**：钙钛矿湿度降解这样的材料物理命题，其 `scope_check` 是"人群/地区/时期"；
数学存在性命题拿到"样本外评估方案与基线比较"。同一批文案散布在 6 个文件：

| 文件:行 | 文案 |
|---|---|
| `research/problem_formulator.py:182,198,254` | 人群/地区/时期、样本外评估 |
| `research/adversarial.py:246,250` | 人群/地区/时期 |
| `research/capability.py:103,259` | 样本外评估 |
| `research/acceptance.py:187` | 未限定人群/地区/时期 |
| `research/verification_service.py:546` | 缺少人群/地区/时期范围 |
| `research/question_planner.py:133` | 需补充人群/地区/时期 |

**附带发现（kind 语义冲突）**：`predictive` 命题的"样本外评估"义务复用了 `kind="design_feasibility"`，
与 `design_feasibility.py`（2-(v,k,λ) 设计存在性判定）**同名不同义**。任何按 kind 聚合的看板/门槛都会把
这两类义务混在一起。

**建议**：`scope_check` 的措辞按研究类型分支（材料/物理：温度/湿度/尺度范围；临床/社会：人群/地区/时期），
并把"样本外评估"另立 `kind`（如 `predictive_validation`）。
