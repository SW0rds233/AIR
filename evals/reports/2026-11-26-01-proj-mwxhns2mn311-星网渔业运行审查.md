### P-4（渲染/写作）确定性草稿把 Python dict 的 repr 写进正文，`{` 未闭合

**现象**：`manuscript.tex:117`（第 5 节「验证建议 (未执行)」）是 **831 字符的单行**：


## 8. 附：`OpenAIConnectionError` 成因追查

> 补记于 2026-11-26 20:55，回答"这个错误到底是什么原因"。全部结论可由本轮产物 + 本机现场实测复现；命令见 §8.8。

### 8.1 这个错误类是什么意思

```
E:\AIR\.venv\Lib\site-packages\langchain_openai\chat_models\base.py:602
class OpenAIConnectionError(openai.APIConnectionError, ModelConnectionError):
    """OpenAI connection error classified as a LangChain model error."""
```

`Connection error.` 是 openai SDK 给 `APIConnectionError` 的**默认文案**；真正原因藏在异常的 `__cause__` 里（`httpx.ConnectError` / `ReadError` / `RemoteProtocolError` / `ConnectTimeout`）。语义只有一个：**这条 HTTP 请求没有在传输层跑完**。

它**不是**下列任何一种（各有对应类，本轮均未出现）：

| 情形 | 实际会抛的类 | 本轮是否出现 |
|---|---|---|
| 限流 429 | `OpenAIRateLimitError` | 否（每次 `payload` 只有 `failures: 1`，无服务端拒绝） |
| 鉴权 401 / 403 | `OpenAIAuthenticationError` / `OpenAIPermissionDeniedError` | 否 |
| 服务端 5xx | `OpenAIAPIError` | 否 |
| 300 s 读超时 | `OpenAITimeoutError`（AIR 会另记 `llm_timeout` 事件） | 否（本轮 0 条 `llm_timeout`） |
| 上下文超长 | `OpenAIContextOverflowError` | 否 |

AIR 的归类路径：`src/utils/network_budget.py:151-152` 的 `network_error()` 按**类名包含 `connection`/`connect`/`timeout`/`readerror`** 判定 → `OpenAIConnectionError` 命中 → 计入网络失败 → 触发降级。

### 8.2 四次失败的实际形态

`src/config.py:142-152` 的客户端是 `ChatOpenAI`（`base_url=https://api.deepseek.com`、`httpx.Timeout(300, connect=10)`、**`max_retries=0`**），所以每次 `llm_started` 对应**恰好一次** HTTP 尝试，没有 SDK 内部重试。

| 时刻(UTC) | 任务 | 角色 | `llm_started` → 出错 | 形态解读 |
|---|---|---|---|---|
| 12:03:50 | task-9309bc3a | evidence | **16 s** | 与 `connect=10s` 上限同量级：连接阶段被拖死、或 SYN 被丢弃后重传耗尽 |
| 12:11:53 | task-d89ff78d | writing | **16 s** | 同上 |
| 12:12:05 | task-ee7b2689 | review | **12 s** | 同上 |
| 12:13:27 | task-30130ed4 | review | **82 s** | 连接已建立、后续被中断（读上限 300 s，故不是读超时） |

三点排除：

1. **不是服务端拒绝**：干净的拒绝（连接被立即 reset / 端口不可达）会在毫秒级失败，不会用 12–16 s；
2. **不是超时**：300 s 读超时会走 `llm_timeout` 分支并记 `ModelCallTimeout`，本轮没有；
3. **不是持续断网**：**每次报错后同一任务立刻又成功**——evidence 12:04:01 `llm_started` → 12:04:09 `llm_result`，随后连续十余次成功；writing 12:10:28 → 12:11:37 一次成功耗时 69 s。正常调用 1–3 s，慢的 20–40 s。

⇒ 判定：**偶发的单次传输层中断**，不是端点不可用、不是限流、不是配额。

### 8.3 产物只能追到这一层

`src/agents/runtime.py:250-252`：

```python
self._on_event("llm_deferred" if deferred else "llm_error", {"task_id": self._task_id,
                              "agent": self._stage,
```

只留 `类名: 文案`，**丢掉 `exc.__cause__`（到底是 `ConnectError` 还是 `ReadError`）和 `exc.request.url`**。所以 919 条事件里 4 条错误记录都只有一行 `OpenAIConnectionError: Connection error.`，无法事后区分"连不上"与"连上后被打断"——§8.2 的形态判断只能从耗时反推。

这本身是个观测缺陷（见 §8.7 第 1 条）。

### 8.6 放大器：一次抖动报废一个环节

| 设计点 | 代码 | 效果 |
|---|---|---|
| SDK 不重试 | `src/config.py:148-149`（注释：*Team runtime owns retries and the wall-clock deadline; no SDK retry stack*） | 有意为之，避免双重重试 |
| 运行时也不重试 | `src/utils/network_budget.py:216-227`：识别为网络错误后只 `failures += 1` 然后 `raise` | **单一抖动即整次调用失败** |
| 兼容名被置 0 | `src/config.py:228` `LLM_MAX_RETRIES = 0` | 没有任何"模型调用重试"实现 |
| 累计 3 次才冷却 | `NetworkBudget(max_failures=3)` | 前两次错误各自静默毁掉一个任务 |
| 冷却后不等待 | `src/graph/research_graph.py:663-667` | 见 P-2 |

逐个对应本轮的损失：

- evidence 一次抖动 → 第 4 个证据任务中止，全轮只有 65 条证据（P-3/P-7 的根）；
- writing 一次抖动 → 第 3 章节放弃，全篇退化为确定性草稿（P-4/P-5 的根）；
- review 一次抖动 + supervisor 重试再抖一次 → `unreviewed`。

**网络问题本身只造成 4 次、每次 12–82 秒的停顿；是这个放大器把它放大成了整轮质量崩塌。**

### 8.7 落地建议（按性价比）

| 序 | 改动 | 位置 | 规模 |
|---|---|---|---|
| 1 | 错误链入事件：记录 `exc.request.url` 与 `__cause__` 链 | `src/agents/runtime.py:250-252` | 小（~5 行） |
| 2 | 对 `APIConnectionError` 做 1–2 次短退避重试（0.8 s / 2 s，受 `budget.remaining()` 约束），复用已有的 `retry_wait()` 会计 | `src/utils/network_budget.py:128-146`（`model_call`） | 小（~25 行） |
| 3 | 区分"网络失败"与"内容失败"：writing/review 遇网络类异常时标"可续做"，而不是立刻降级确定性草稿 | `src/agents/writing.py:159-172` | 中 |
| 4 | 冷却等待（P-2 本体） | `src/graph/research_graph.py:663-667` | 中 |

第 1、2 条合计约 30 行，效果是把"一次抖动 = 一个环节报废"变成"一次抖动 = 慢 3 秒"。**建议先做 1（否则下次仍然只能猜），再做 2。**
