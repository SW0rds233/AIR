# 第一部分：PDF 渲染失败（已解决）

## 1. 现象与证据链

`manifest.json`：

```
compilation_status      : "failed: LaTeX 编译报错, 输出可能被截断:"
publication_gate_reasons: ["正文引用了不存在的章节: 3.1, …6.3",
                           "LaTeX 编译失败: failed: LaTeX 编译报错, 输出可能被截断:"]
pdf                     : ""            ← 清单里认为没有可交付 PDF
```

而 `manuscript.pdf` 确实存在（124 KB），`pdfinfo` 报 **3 页**，日志末尾是
`Output written on …manuscript.pdf`。所以这次不是"没有 PDF"，而是**PDF 被截断成 3 页**。

编译日志里的唯一一处致命错误（`manuscript.log:965`）：

```
! You can't use `macro parameter character #' in display math mode.
l.62 ...^{668}s_i=\mathbf{0}\ \Longrightarrow\ \\#
                                              \{i:s_i(k)=+1\}=\\#\{i:s_i(k)=-1\}=334\quad(\forall k)
```

对应的 `.tex` 第 62 行：

```latex
\begin{equation}\sum_{i=1}^{668}s_i=\mathbf{0}\ \Longrightarrow\ \\#\{i:s_i(k)=+1\}=\\#\{i:s_i(k)=-1\}=334\quad(\forall k)\end{equation}
```

## 2. 根因：`\#` 被**二次转义**

模型在公式里自己写了 `\#`（基数的转义写法，这是正确的 LaTeX）。而 `escape_math` 当时是无条件替换：

```python
body = body.replace("%", r"\%").replace("#", r"\#")   # ← 不看前面有没有反斜杠
```

于是 `\#` → `\\#`。在 LaTeX 里 `\\` 是**换行**，紧跟的 `#` 变成"裸的宏参数字符"落在 display math 里 → 致命错误。因为编译器带 `-halt-on-error`，**编译就此停止**，30 KB 的稿件只写出前 3 页。

同一类"已转义的又被转一次"的问题在 `escape_latex` 里同样存在（`& % # _` 四个字符都是无条件 `replace`），只是这次先被公式里的 `\#` 触发。

> 说明：编译器的判定**是对的** —— 上一轮我合回的 `!` 错误行检测正确地把它判成失败，没有把截断的 PDF 当成成功。问题在渲染器，不在判定。

## 4. 修复内容（`src/publication/render_latex.py`）

1. **`_escape_active()`：只转义"还没转义过"的字符。**
   `re.sub(r"(?<!\\)" + char, …)` —— `\#`/`\%`/`\&`/`\_` 原样保留，裸 `#`/`%`/`&`/`_` 才转义。
   同时用在 `escape_latex`（4 个字符）与 `escape_math`（`%`、`#`）上。

2. **调整顺序：行内数学识别提前到 Unicode 映射之前。**
   实测 `{+1,−1}^668` 里的 `−` 会先被映射成 `$-$`、`Σ_{t=0}^{166}` 的 `Σ` 先变成 `$\Sigma$`，把待识别的形状切碎，`^` 只能退化成脱字符。现在先识别、后映射。

3. **新增 `_math_body()`**：行内数学片段的**内部**也做 Unicode → 数学命令转换，避免 `{+1,−1}` 里的 U+2212 带着 Unicode 落进数学模式。

4. **新增 `_INLINE_SUBSUP_RE`**：识别 `Σ_{t=0}^{166}` 这种"上下标同时出现"的形状（必须排在单独的上标/下标规则之前，否则会被拆成两半）；底数同时支持 ASCII 字母数字与希腊字母。

5. **补齐缺字形表**：`↦ ᵀ ⟹ ⌊ ⌋ ⌈ ⌉ ≔ ≢`，以及上/下标数字字母 `⁰¹²³⁴⁵⁶⁷⁸⁹ ⁿ ₀₁₂₃₄₅₆₇₈₉`。
   （这些不是猜想：`↦ ᵀ ⌊ ⌋` 是本轮日志实际报出的，`≢ ⁸` 是重渲染后新暴露的。）

6. **`_exponent()` 也过 `_math_body`**：`^{668×668}` → `^{668\times668}`。

## P0-3 本地资料库读取**全线崩在同一个错字上**（已复现）

定位到 `src/kb/service.py:420`：

```python
return SourceRef(source_id=doc_id, chunk_id=f"{doc_id}#{chunk['index']}", …)
```

而 `chunks` 表的列名是 **`idx`**（`src/kb/store.py` 建表语句：`chunks(doc_id, idx, section_index, page, text, …)`），`get_chunks()` 也按 `idx` 取名返回。**已用真实资料库复现**：

同一函数里 `page/char_start/char_end` 都用 `.get(...)`，**只有 `index` 用了 `[...]`，而且名字错了**。后果是链式的：任何"回到原文"的读取都抛异常 → 本地库被判"不可用" → 证据全部退化为摘要 → 本轮 33 条证据里 **23 条 abstract、5 条 metadata、只有 5 条 fulltext**，`unresolved.md` 也自述"全部结论基于摘要级证据"。
