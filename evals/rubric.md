# 领域人审表（计划书 §5 门槛 6）

用途：对计划书 §5 固定的端到端验收题做**领域专家人工复核**。自动化测试能证明
"系统没有越界、状态一致、资料不混用"，但**不能**证明"模型忠实于领域、论证在领域内成立、
引用恰当、建议真的能区分两种解释"——那需要领域专家签字。

本表不替代自动化测试；两者都通过才算交付达标。

---

## 0. 送审材料

一次送审应包含同一次运行（`run_id` 一致）的下列文件，缺一项即视为材料不全：

| 材料 | 来源 | 检查 |
|---|---|---|
| 运行身份（project / problem / run / branch） | `manifest.json` | 与工作台显示一致 |
| 研究规格（原始请求、问题、变量域、资料源绑定） | `research_spec.json` | 与实际研究的问题一致 |
| 结论与状态 | `claims.json` + 工作台 | 每条结论都有状态/支持方式/覆盖范围 |
| 论证链（条件→步骤→义务→验证输入→反例/未决） | `manuscript.md` "证明与验证" 段 | 关键步骤可逐步复核 |
| 验证记录与证书 | `verification/` + `obligations.json` | 局部验证未被写成整体证明 |
| 证据与逐命题归属 | `evidence.json` + `evidence_links.json` | 每条引用可回查原文定位 |
| 已有工作对照 | `novelty_review.md` | 逐项差异（前提/模型/结论/方法/适用域） |
| 实验/仿真建议 | `experiment_specs/` | 明确"建议/未执行"；有判据 |
| 未决问题与缺口 | `unresolved.md` | 未关闭义务、写作缺口如实列出 |
| 资源用量与停止原因 | `delivery_gate.md` | 实际花费与预估分开 |

## 1. 端到端验收题（计划书 §5 固定）

输入："结合我选定的资料库，分析信道变化对射频指纹可分性的影响，并给出理论结论与仿真建议"。

验收者需**事先准备**（评审前不得交给系统）：

1. 两篇条件不同的资料（例如不同信噪比区间、不同设备集），用于检验条件比对；
2. 一个已知解析特例（可作为回归锚点）；
3. 一个会推翻过强结论的反例（检验系统是否拒绝把结论写成无条件成立）。

## 2. 评审维度与判定

每个维度给出 `通过 / 需修改 / 不通过`，并**必须写具体理由与所依据的文件位置**。
"看起来合理"不算通过。

### 2.1 研究意图（是否研究了被问的问题）

- [ ] 系统复述的研究问题与用户请求一致（不是把"影响"直接当成一条因果结论套模板）；
- [ ] 变量、量纲、适用范围明确；
- [ ] 若问题无法形式化，系统请求澄清而不是给出占位结论。

### 2.2 资料与来源（用没用对资料）

- [ ] 显示了实际使用的资料源版本（`source_set_id` 与文档数/版本）；
- [ ] 结论引用的证据**只能来自所绑定的资料源**；
- [ ] 每条引用有可回查定位（页码/节号/定理号/片段 hash）；
- [ ] 转引同一原始记录的多次引用没有被算成独立支持。

### 2.3 模型忠实度（模型是不是真的描述了该领域）

- [ ] 至少两个候选机制，且给出舍弃理由（问题忠实度、来源条件、可验证性、成本）；
- [ ] 模型到数学表达的对应关系可检查（术语、量纲、边界与噪声假设）；
- [ ] 明确列出**未覆盖的现实因素**；
- [ ] 模型间冲突预测被转成可区分检验，而不是被抹平。

### 2.4 论证与验证（结论站不站得住）

- [ ] "证明与验证"段给出可逐步复核的论证链；
- [ ] 每条主要论断能反查到原始证据或验证输入；
- [ ] 局部步骤验证没有被写成整体证明；
- [ ] 工具 `unknown` / 超时 / 编码不一致没有被当成"命题为假"或"已验证"；
- [ ] 反例（若有）满足声明前提，且结论确实被否定。

### 2.5 引用与差异（有没有夸大）

- [ ] 已有工作对照逐项给出相同/包含/条件更强或更弱/无法比较；
- [ ] 没有完成差异分析时**不出现"原创发现"**；
- [ ] 无等价结果时只作有界表述（"在所检索范围内尚未发现等价结果"）。

### 2.6 仿真/实验建议（建议有没有用）

- [ ] 建议针对**具体未决命题或两个竞争模型**，而不是按命题类型套模板；
- [ ] 明确要区分的结果、可操纵/观测变量及单位、参数范围依据；
- [ ] 有对照/消融、误差与灵敏度检查、预计资源；
- [ ] 缺单位/边界/判据时报告缺项，并**维持"草案"**；
- [ ] 没有执行日志时只显示"建议/未执行"，不出现"仿真已验证"。

### 2.7 写作缺口回流（有没有掩盖）

- [ ] 写作阶段发现的缺口如实列在正文，并已回流成研究义务；
- [ ] 回流后的缺口有明确归属（命题 + 版本）与验收方法；
- [ ] 不能由研究循环自行消解的缺口没有被伪装成已解决。

### 2.8 交付诚实度

- [ ] 交付级别（研究备忘录 / 条件性研究报告 / 论文草稿）与实际完成度一致；
- [ ] 未决项、预算停止原因、资源用量如实显示；
- [ ] 未能得出足够强结论时，交付的是条件性结果而不是包装过的断言。

## 3. 失败案例与修改记录（必须保留）

每个 `不通过` 项都要留下一条记录，便于下一轮回归：

| 编号 | 日期 | 维度 | 现象（含文件/行位置） | 期望 | 处理 | 状态 |
|---|---|---|---|---|---|---|
| R-001 | | | | | | 待处理 |

处理状态取值：`待处理 / 已修复(测试名) / 判定为非缺陷(理由)`。
**不允许**把"判定为非缺陷"留空理由，历史记录也**不得删除**（只允许追加处理说明）。
